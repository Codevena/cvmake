# Release 0.2.0 — review record

Two review gates ran before this change was committed: a plan gate (three rounds)
and a definition-of-done gate (three rounds plus a verification round). Each round
used one executing reviewer with repo read and execute access, and one reading
reviewer working from an inline payload.

This file exists because the working directory that held the full transcripts is
temporary. It records the verdicts and the measurements behind them.

## The four defects that would have shipped

**The CLI could not start at all.** `packages/core` imported Puppeteer statically
while declaring it an *optional* peer dependency. Because the CLI entry point
loads every command eagerly, a clean install killed `--help`, `init`, `validate`
and `list-templates` too. Measured end to end: `cvmake init` — the first command
the README documents — exited 1 with `ERR_MODULE_NOT_FOUND` from a packed,
installed tarball.

**`pnpm publish` cannot authenticate.** The workflow published with pnpm 9.12.0;
OIDC trusted publishing landed in pnpm 10, and the NPM_TOKEN had already been
removed. The tag push would have built, tested, and then failed at auth.

**`npm publish` from a package directory ships `workspace:*`.** The obvious fix
for the previous point — switch the client to npm — was measured and rejected:
`npm pack ./packages/core` retains `"@codevena/cvmake-schema": "workspace:*"`,
which npm rejects on the consumer side with EUNSUPPORTEDPROTOCOL. Six such
references exist across three packages. The release now packs with pnpm and
publishes those tarballs with npm; both tools are required and neither suffices.

**A tarball could be published under a foreign package name.** Twice, at two
depths. First: the filename was trusted and the packed manifest never read.
Then, after that was fixed: npm strips the leading path component on extract, so
a second manifest under `other/package.json` overwrites the one that was
validated. Both were measured with real `npm publish --dry-run`, which reported
`+ @codevena/incorrect-package@0.2.0`. Archive structure is now validated —
a single `package/` root, exactly one regular `package/package.json`.

## Mutation evidence

Every new guard was seen red in a copy before being trusted. The real repository
was never mutated.

| Guard | Mutation | Result |
|---|---|---|
| `isSameFile` collision check | replace dev/ino comparison with `a === b` | the hard-link case fails; unrelated cases stay green |
| `isSameFile` error handling | drop the non-ENOENT rethrow | throws-assertion fails |
| lazy Puppeteer import | restore the static import | **only** S2 of the smoke test fails (2/16) |
| Puppeteer as a real dependency | restore the optional peer declaration | **only** S1 of the smoke test fails (1/16) |
| dynamic-import interop | return the raw namespace without unwrapping `.default` | 6/6 in `pdf-lifecycle.test.ts` fail |
| registry-source check | restore the `.tgz` suffix predicate | an injected registry entry passes unnoticed (16/16 green) |
| S2 diagnostic assertion | disable the positive predicate | an unrelated failure passes as success |
| publish version gate | disable the packed-version comparison | four publishes proceed instead of aborting |
| accounting guard | `PACKAGES = []` | exits 1 as intended |

The collision guard's two numbers, executed rather than asserted: without it,
`cvmake build cv.yaml -o cv.yaml` exits 0 and the input YAML is overwritten with
PDF bytes; with it, exit 1 and the file is byte-identical.

## One near-miss worth recording

The first fix for the archive-structure check parsed `tar -tvf` and located the
filename after an `HH:MM` timestamp. tar prints a *year* instead of the time once
a file is older than six months, so the parser mistook metadata for the path and
rejected a valid CLI tarball. It would have blocked every legitimate release.

It surfaced only because the test included a control case with valid tarballs.
Verifying that an attack is rejected proves nothing on its own: a guard that
rejects everything is indistinguishable from a working one, unless something
also confirms the good case still passes.

## What no gate here can prove

- **Authorisation.** The publisher validates artifacts, never permissions, and
  `npm publish --dry-run` does not touch registry auth. A trusted publisher
  configured for three of the four packages publishes three and fails on the
  fourth, irreversibly. All four configurations were checked by hand on
  2026-09-09 — each carries a GitHub Actions publisher for Codevena/cvmake with
  `release.yml`, no environment, and both `npm publish` and `npm stage publish`
  permitted. That check is a snapshot, not a guarantee: it has to be repeated if
  the package set changes.
- **The first real run of this workflow.** No git tag has ever existed in this
  repository; 0.1.0 was published manually. Every job here was linted, parsed and
  locally exercised, but the tag-triggered path itself runs for the first time.
- **Chromium under the reviewers' sandbox.** Browser-backed gates were green
  locally (`pnpm -r test:integration` with Chromium 148) but blocked for the
  executing reviewer; it recorded this as could-not-run rather than reviewing by
  reading.
